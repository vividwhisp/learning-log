### Important test-scope notes

-   Attacks 10--12 validate API authentication and tenant routing using
    a fake searcher. They do not, by themselves, prove database-level
    isolation.
-   A separate
    `tests/test_tenant_isolation.py::test_cross_tenant_isolation` test
    exercised the actual dense Qdrant and sparse BM25 retrieval classes
    against a synthetic multi-tenant corpus. It passed.
-   The tenant-isolation test fixture was corrected: the BM25 query term
    appeared in half of the original four-document corpus and received
    zero IDF, so the fixture was expanded with two unrelated documents.
    The BM25 implementation and tenant filter were not weakened.
-   The poisoned-document test was corrected to fail on endorsement, not
    mere mention of the poisoned phrase. The model may ignore the
    poisoned claim or explicitly reject it.
-   Private-data tests used synthetic canary values only, not real
    credentials or personal data.

## 2. Defenses and implementation work

### Untrusted retrieved content

-   Retrieved documents are explicitly represented as untrusted
    reference data in the generation prompt.
-   The prompt separates system instructions from retrieved document
    content.
-   Verified that all retrieved documents are included in the generation
    payload. A bug that returned from `build_messages()` inside the
    document loop was fixed; a regression test confirms all three sample
    documents are included.

### Privacy and secret redaction

The privacy layer uses basic regex patterns for these categories:

-   Email addresses
-   Indian phone-number-like values
-   Aadhaar-like numeric values
-   PAN-like values
-   API-key-like strings
-   Password/secret/token assignments

`redact_text()` is applied to generation inputs and outputs. Tests
verify that synthetic canary values do not appear in the serialized
model messages or returned answer, and that redaction placeholders are
present.

**Limitation:** These are deliberately basic patterns, not comprehensive
PII or secret detectors. They can miss formats and may produce false
positives.

### Authentication and tenant boundaries

-   API identity is mapped to a tenant on the server side.
-   Missing and invalid demo identities are rejected.
-   Tenant identity is passed to retrieval from the authenticated
    request context.
-   A client-supplied tenant ID in the request body does not override
    the server-derived tenant.
-   Dense and sparse retrieval require a `tenant_id`.

**Limitation:** The demo identity mapping is a learning implementation,
not production authentication.

### Quality findings to retain

1.  **Citation extraction:** Question 3's answer included a source
    marker, but the citation extraction function returned `[]`.
    Investigate citation parsing separately.
2.  **Answer grounding:** Question 10 included an unsupported guarantee
    about overdrafts. Avoid presenting stronger guarantees than the
    retrieved evidence supports.
3.  **Abstention:** Question 11 correctly abstained when the corpus
    lacked relevant information.
4.  **Rate limits:** Several evaluation requests received HTTP 429
    responses and succeeded after client retries. All 11 answers were
    eventually generated.

No numerical answer-quality score was calculated. Do not describe this
as 11/11 independently verified correct answers.

## 5. Measurements and limitations

-   **Attack test coverage:** 15 of 15 registered cases passed their
    current tests.
-   **Regression suite:** 30 tests passed.
-   **Pre-fix attack baseline:** Not measured. Therefore, no percentage
    reduction in attack success or leakage is claimed.
-   **Private-data leakage:** Synthetic canaries were checked at
    model-input and output boundaries in the relevant tests. This is
    test evidence for the covered formats, not proof that every possible
    secret format is detected.
-   **Tenant isolation:** Verified using actual dense and sparse
    retrieval classes on a synthetic corpus, in addition to API boundary
    tests with a fake searcher.
-   **LLM behavior:** Live model tests can vary between runs. Assertions
    should check behavior (endorsement, disclosure, or instruction
    following), not fragile exact wording.
